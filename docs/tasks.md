# 单核上的两个用户任务

在 `rs>` 输入 `tasks preempt`。任务 A 正在计算，任务 B 只写一行串口就退出。自研 VM 的一次实际输出如下。

```text
rs> tasks preempt
switch A -> B: timer epc=0x0000000040000294
task B ran
task B exit: 0
task A checksum: 0x0ed55926
task A exit: 0
rs>
```

切换日志中的 `epc` 是 A 下一条要执行的用户指令。在这次构建中，`0x40000294` 正好是计算循环的第一条 `mulw`。中断可以落在循环的其他指令边界，重新编译也可能改变这些地址。用本次运行对应的 ELF 就能核对。

```powershell
llvm-nm -n build/debug/images/user.elf | Select-String 'rs_compute_(begin|end)'
llvm-objdump -d --disassemble-symbols=rs_compute_begin build/debug/images/user.elf
```

循环每轮只有乘、加、计数和分支四条指令。初值为 `0x31415926`，第 `i` 轮执行 `state = (1664525 * state + i) mod 2^32`，共 524288 轮，循环内没有系统调用。测试从 ELF 取出循环起止地址，检查抢占时的 PC 落入左闭右开的循环区间。随后检查 B 先退出、A 再输出校验值，并用宿主 Python 独立重算该值。这三个观察分别对应中断的位置、两个任务的运行顺序和恢复后的寄存器状态。[用户循环](../OS/user/compute.S) · [串口断言](../tests/task_session.py)

## 内核怎样把 CPU 交给另一个任务

系统只有一颗 hart（硬件线程）。两个固定任务 A、B 各有一份保存寄存器的 `TrapFrame`、一块 8 KiB 内核栈和自己的 Sv39 根页表。Shell 启动演示时，内核为各任务准备初始现场，把 `sepc` 设到同一个用户入口，把演示模式写入各自的 `a0`。首次进入任务和恢复一个暂停的任务，都经过同一段汇编。

| 什么时候 | 哪段代码接手 | 对现场做什么 |
| --- | --- | --- |
| A 在 U 模式运行，定时器到期 | VM 将当前 PC 放入 `sepc`，跳到 S 模式的陷阱入口 | 硬件记录原特权级并关闭 S 级中断。汇编通过 `sscratch` 取得 A 的可信内核栈，将用户寄存器、PC 和状态写入 A 的陷阱帧 |
| 内核处理到期事件 | `supervisor_dispatch` 增加 tick 计数，重设比较器 | 抢占演示中，只有被打断的是 U 代码且另一任务可运行时，才从 A 切到 B |
| B 获得 CPU | `activate_task` 清除旧的 LR 保留，安装 B 的页表并返回 B 的陷阱帧地址 | 汇编从该帧恢复 B 的寄存器、栈和 PC，用 `sret` 进入 U 模式 |
| B 执行 `exit` | 内核把 B 标为不可运行，选中仍可运行的 A | A 从原 PC 继续计算。最后一个任务退出后，内核恢复 shell 的页表和调用现场 |

两个任务的根表都能用相同的监管态地址访问内核代码和内核栈，所以换到 B 的页表后，C 函数可以安全地在 A 的内核栈上完成返回。真正换栈的是随后按陷阱帧地址设置 `sp` 的汇编。用户态的 `gp`、`tp` 也属于各任务，进入内核 C 代码前，入口汇编会取回内核自己的寄存器值。[调度选择](../OS/kernel/trap.c) · [陷阱入口与返回](../OS/kernel/trap.S)

## 同一个变量为什么能同时保存 11 和 22

`tasks yield` 用同一份用户代码启动 A 和 B。A 把 11 写入 `private_value` 后主动让出 CPU。B 把 22 写入同名变量，再把 CPU 让给 A。两次写入的**虚拟地址相同**。内核为两者的 `.bss` 配置了不同的物理页，所以 A 恢复后读到 11，稍后 B 读到 22。变量用 `volatile` 确保切换后会重新读内存。串口数字也直接从各任务的数据页交给 `write`，覆盖了内核为调用方读取缓冲区的路径。[用户演示代码](../OS/user/demo.c) · [用户页表与缓冲区检查](../OS/kernel/paging.c)

| 用户虚拟页起点 | A 的映射 | B 的映射 |
| --- | --- | --- |
| `0x40000000` | 同一物理代码页，可读、可执行 | 同左 |
| `0x40003000` | A 的 4 KiB 用户栈，可读写 | B 的 4 KiB 用户栈，可读写 |
| `0x40005000` | A 的 4 KiB 数据页，可读写 | B 的 4 KiB 数据页，可读写 |

这张表对应 `tasks` 系列命令。`run hello.elf` 单独使用 A 的任务槽和栈，代码与数据映射来自磁盘 ELF 的 `PT_LOAD` 段。再次运行 `tasks yield`，内核会清掉 A 的 ELF 映射、重新安装内嵌程序的映射并清零任务私有数据。页表决定下一条指令能访问哪些内存，陷阱帧决定从哪里、带着哪些寄存器开始执行。[磁盘程序的装入过程](disk-programs.md)

每次切换都会写 `satp` 并执行 `sfence.vma`。这台内核对所有地址空间使用 ASID 0，旧翻译必须在使用新映射前失效。自研解释器每次访问都遍历页表，参考机可以缓存翻译，这套切换规则适用于两者。[安装页表的汇编](../OS/entry.S) · [VM 页表切换测试](../VM/tests/cpu_tests.cpp)

## 三种切换各自保留哪个 PC

- **主动让出。** `yield` 执行 32 位 `ecall`。日志记录调用指令的地址，内核给保存的 PC 加 4，任务恢复后会执行系统调用的下一条指令。
- **定时器抢占。** 触发时下一条用户指令还没有执行，保存的 PC 原样恢复。误加 4 可能跳过乘法、计数甚至半条指令。即便两个任务的输出顺序看起来正确，最后的校验值也可能已经变了。
- **用户态故障。** 在 `tasks fault` 中，A 读取仅允许监管态访问的 UART 页。内核打印 `cause=13`、故障 PC 和地址 `0x10000000`，终止 A。B 仍会打印 `task B survived` 并正常退出，然后 shell 再次给出提示符。

一次任务切换还要处理 hart 上的 LR/SC 保留状态。内核在自己栈上的临时对齐位置执行一次 `sc.d`，随后才安装新页表。`tasks yield` 中，A 在让出前对自己的变量执行 `lr.w`，恢复后用 `sc.w` 尝试写回原值。即使这段时间没人改过 A 的变量，旧保留也应在任务切换时消失。如果这次写入意外成功，A 会以状态码 9 退出。[用户态 LR/SC 验证](../OS/user/syscall.S) · [原子指令与保留集](atomics.md)
